### 0.2.2 上线回退：OJ tpmC ~950 → ~800（2026-07-09 晚）

把 §0.2.1 的默认 80μs push 到 OJ 后，实测 tpmC 从 S5.1+S6+S7.1 的 **~950** 掉到 **~800**（几乎回到 2026-07-05 最初基线 799.83），本地 30s+360s×3 A/B 却测出「差异 −0.87%，噪声内」的中性结论——本机结论与线上结果直接矛盾。

**根因推断**（未在 OJ 机器上直接验证，但是当前最合理的解释）：`flush_worker` 里 `first_round` 的门槛（有 committer 在等 + 没人等缓冲空间）在正常负载下**几乎每个刷盘批次都会触发一次**，即几乎每次 commit 都要走一次 `std::this_thread::sleep_for(80us)`。本机是低负载独占裸机，`sleep_for` 的实际唤醒延迟接近请求值（~80μs 量级）；但 **`sleep_for`/`nanosleep` 的实际唤醒精度高度依赖内核调度器状态**——在虚拟化、共享 vCPU、或线程数远超核数的环境下，睡眠到期后线程要等下一次被调度器实际换上 CPU 才能继续执行，这个延迟可以是几百微秒到数毫秒，比请求的 80μs 大一个数量级以上。OJ 判题机大概率是这种环境（多客户端线程 + 服务端多线程共享有限核数），意味着**几乎每次 commit 都被多加了一次不可控的、可能达毫秒级的调度延迟**，直接把 commit 墙钟拉长，tpmC 应声下跌。

**已执行的止损**：`group_commit_window_us_` 默认值改回 **`0`（关闭）**，`RMDB_GROUP_COMMIT_WINDOW_US` 仍保留、仅供本地/未来受控实验使用，不再默认生效。已重新编译、`run_tests.py` 11/11 PASS 确认回退无副作用；commit `9726c6a` 已 push 到 `gitee`。

**回退效果确认（2026-07-10）**：线上复测 **tpmC 显著回升**，印证了「`sleep_for(80us)` 在 OJ 判题机上的实际调度唤醒延迟远超本机裸机」这一根因推断——本次事故是诊断-回退-验证闭环完整跑通的一个真实案例，不只是猜测。

**教训**：

1. **本机测出的"中性/无回归"不能代表 OJ 判题机的调度行为**——尤其涉及微秒级 `sleep_for`/`usleep`/自旋等待这类对调度器延迟极度敏感的机制，本机裸机环境是最乐观的情况，不是有代表性的下限。
2. 硬编码非零默认值本身没错（前提是机制真的有收益）；错在**没有先在更贴近 OJ 特征的环境（多线程争抢同一批 vCPU、限核 cgroup 等）里验证过 `sleep_for` 的实际唤醒精度**就直接上线。
3. 若后续要重新尝试 S5，应换一种对调度延迟不敏感的触发机制（**字节 / 等待者阈值**，见 §2.A.2），**不再使用固定时长 `sleep_for`**。

## 1. 背景

S3 后 NewOrder profile 顶项仍是 commit 等日志持久化。组提交窗口目前几乎完全依赖 **一次 fsync 的自然耗时**（换缓冲后锁外 sync，期间新日志进另一块 `bufs_`）。若 fsync 很快，或 commit 请求到达稀疏，批尺寸偏小，仍接近「每批少量 commit 付一次 fsync」。

---

## 2. 方案包

### 2.A 微批 `wait_for_persist`

#### 2.A.1 时间阈值 `sleep_for`（❌ OJ 证伪，默认已关闭）

**思路**：`flush_worker` 从空闲唤醒的本批第一轮，短睡（如 50–200μs）让更多 committer 抬高 `requested_lsn_`，再统一刷盘。对照 ClickHouse 历史 WAL 旋钮（[§7 §2](./7.外部参考-DuckDB与ClickHouse.md#2-s5commit-7173)）：`write_ahead_log_interval_ms_to_fsync`。**OJ 已证伪，勿再默认启用。**

**结果**：本机 30s+360s×3 A/B 为噪声内中性；**OJ 默认 80μs 上线后 tpmC ~950→~800**；回退后恢复 ~950（§0.2.2）。根因：`sleep_for` 在判题机（疑虚拟化/共享核）上实际唤醒延迟远超请求值，而 `first_round` 几乎每批都触发。

**勿再默认启用**；`RMDB_GROUP_COMMIT_WINDOW_US` 仅作本地受控实验。

#### 2.A.2 字节 / 等待者阈值（S5.2+，未做，若重试优先此方向）

**思路**：积压日志 ≥ M 字节，或 `persist_cv_` 等待者 ≥ N，再触发换缓冲 + fsync；**不依赖 `sleep_for`**，对调度延迟不敏感。对照 CH `write_ahead_log_bytes_to_fsync` + 等待者计数。

注意（两条路径通用）：

- 仍须 **正确唤醒**；超时后必走现有 `request_flush`。
- **不可**为吞吐跳过 fsync；kill -9 恢复仍是正确性红线。

### 2.B `write_log` 大块 / 批写（可选）

对照 DuckDB `BufferedFileWriter`：大块直接写，少拆碎 syscall。检查 `DiskManager::write_log` 是否对整块 `LogBuffer` 一次 `write`；避免多余 memcpy。

### 2.C 日志对象开销（P3，顺带）

`CommitLogRecord` 等多用栈对象；语句级 INSERT/UPDATE 日志若频繁堆分配，可对象池。**不是 S5 主收益**。

### 2.D 明确不做

| 不做 | 原因 |
|------|------|
| 固定时长 `sleep_for` 微批 | OJ ~950→~800；本机测不出 | §0.2.2 |
| checkpoint 时跳过 WAL（DuckDB 可选路径） | OJ 崩溃恢复 |
| 去掉 `wait_for_persist` | 耐久性 |
| 再引入第三把「大锁」 | 已拆 append/persist |
