## P0：WAL 管道统计（先测量，半天）

**目的**：回答两个问题——① 每次 fsync 实际覆盖几笔 commit（批次聚合效率，理想 ≈ 并发 committer 数）；② fsync 耗时分布。P3 做不做、P1 预期多大收益，都由这两个数决定。

### 改动（仅 `log_manager.{h,cpp}`）

```cpp
// LogManager 新增（relaxed atomic，常开，开销可忽略）
struct WalStats {
    std::atomic<uint64_t> n_fsync{0};          // fsync 次数
    std::atomic<uint64_t> fsync_us_total{0};   // fsync 总耗时
    std::atomic<uint64_t> fsync_us_max{0};
    std::atomic<uint64_t> n_bytes{0};          // write_log 总字节
    std::atomic<uint64_t> n_batches{0};        // 换缓冲批数
    std::atomic<uint64_t> n_commit_waits{0};   // wait_for_persist 进入慢路径次数
    std::atomic<uint64_t> lat_bucket[6]{};     // fsync 延迟桶 <1/1-5/5-10/10-20/20-50/>50ms
};
```

- `wait_for_persist`：`persist_lsn_ < target` 时 `n_commit_waits++`。
- `flush_worker`：`write_log` 前后记 bytes/batches；`sync_log` 前后 `steady_clock` 计时进桶。
- **输出**：`RMDB_WAL_STATS=1` 时 flush 线程每 10s 向 stderr 打一行汇总（`fsync/s、avg/max us、bytes/batch、commit_waits/fsync`）；析构时再打一次。默认不打印（统计照常累计，无 I/O）。

**关键读数**：`commit_waits / n_fsync` = 每次 fsync 摊到的 commit 数。8 并发下若 ≥4 说明组提交聚合已接近上限（P3 无空间，收益只能来自 P1/P2 缩短单次 fsync）；若 ≤2 说明有串行化点，P3 值得做。

### 验收

`run_tests` 11/11；`bench_tpcc --quick` 无回退；`RMDB_WAL_STATS=1 bench_tpcc --mid` 拿到基线报表存档。

## P1：日志文件预分配 + 批帧（1–1.5 天，预期 OJ 收益最大）

**原理**：文件大小不变时 `fdatasync` 只刷数据块、不写 journal（InnoDB/RocksDB 的 WAL 预分配即为此）。判题机盘越慢此税越重——这可能是 OJ 只有本地一半的重要成分。

### 1.1 写路径（`disk_manager.{h,cpp}` + `log_manager.cpp`）

```cpp
// DiskManager 新增
static constexpr long LOG_PREALLOC_CHUNK = 16L << 20;   // 16MB 一段
long log_prealloc_end_ = 0;                             // 已预分配（零填充）终点

void ensure_log_capacity(long need_end) {
    if (need_end <= log_prealloc_end_) return;
    long new_end = ((need_end / LOG_PREALLOC_CHUNK) + 1) * LOG_PREALLOC_CHUNK;
    if (ftruncate(log_fd_, new_end) != 0) throw UnixError();   // 扩展区读出为 0
    log_prealloc_end_ = new_end;
}

// write_log 改签名：按逻辑偏移 pwrite，不再 lseek(SEEK_END)
void write_log(const char* data, int size, long offset);   // 内部先 ensure_log_capacity(offset+size)
```

`flush_worker` 换缓冲时已知本批起始偏移（摘缓冲时从 `total_offset_` 推得：`batch_start = total_offset_ - 本批字节数`，在 `append_mtx_` 内一并取出），传给 `write_log`。**正常运行期 fdatasync 从此不再有大小变更**（每 16MB 才付一次 ftruncate+journal）。

启动时：`log_prealloc_end_ = get_file_size(LOG_FILE_NAME)`（若非 chunk 对齐说明是旧格式/恢复后状态，首次 ensure 会补齐）。

### 1.2 恢复终点判定：批帧 + CRC（正确性核心）

预分配后不能再用文件大小判终点。零填充区天然让 `read_one` 停下（`tot=0 < HEADER`），**但有一个现状没有的坑**：崩溃时半写的记录——头部完整、体被零填充——会被当成合法记录进 `uncommitted_`，undo 时用「一半真数据一半零」的 old_data 回写行，**破坏数据**（现状靠 `offset+tot > 文件大小` 挡住这种残尾，预分配后文件大小失去这个含义）。

解法：**flush_worker 每批写一个 12B 批头**，恢复按批校验：

```
[u32 magic 0x574C4247][u32 batch_len][u32 crc32(batch body)] [records ...]
```

- `flush_worker`：写批前算 crc32（查表实现 ~50 行，无外部依赖；批仅 KB 级，成本可忽略），一次 `write` 连批头带 body 写出。`total_offset_` 语义改为**含批头**的文件字节偏移（`add_log_to_buffer` 不感知；worker 换缓冲时补加 12）。
- 恢复 `analyze/redo`：外层循环按批推进——读批头，`magic 不符 ∨ len==0 ∨ crc 不符` → 终点；否则用**现有 per-record 解析代码**扫批内记录。残缺批整批丢弃，半条记录不可能混入。
- `undo()` 收尾：`truncate(log_end_)` 保留（切掉崩溃残尾），随后 `ensure_log_capacity` 重建零尾；`init_offset(log_end_)`。
- `db.restart` 偏移语义不变（字节偏移）；检查点 CKPT 记录经 `add_log_to_buffer` → 必然开新批 → 天然批对齐。

**耐久性论证**：commit 记录必在其所属批的 crc 覆盖内；fdatasync 返回 ≤> 整批数据落盘 → crc 校验过 ≤> 批内全部记录完整。未确认的 commit 只可能在残缺批里 → 整批丢弃 → 不会出现「客户端未收到 OK 但恢复出来」以外的任何异常方向（该方向本就允许）。

### 验收

`run_tests` 11/11；**kill -9 崩溃恢复用例必须过**（`bench_tpcc --strict` 内含 + 手工 kill -9 三次采样）；`RMDB_WAL_STATS=1` 对比 P0 基线的 fsync avg/max（本地就应可见下降，慢盘降幅更大）；`bench_tpcc --mid` A/B。

## P2：WAL 瘦身——update 改 byte-diff 增量日志（1–2 天）

**原理**：fdatasync 耗时与脏字节量正相关（尤其慢盘）。stock update 全行 old+new ~680B，实际只改 4 列 ~20B。**做通用 byte-diff，不依赖 col_delta/col_patch 结构**，一处改动覆盖所有 update 路径（stock/district/customer/warehouse…）。

### 2.1 新日志类型（`log_manager.h`）

```cpp
enum LogType: int { ..., CKPT, UPDATE_DELTA };   // 追加，不动旧值

/* payload：u8 tab_name_len + name | Rid | u8 n_ranges |
 *          n × { u16 off, u16 len, old[len], new[len] } */
class UpdateDeltaLogRecord : public LogRecord { ... };
```

- 表名用 `u8 len`（省掉 size_t 8B；表 id 方案需动 `db.meta`，收益仅再省几字节，**不做**）。
- 生成端（`executor_update.h` 现写 `UpdateLogRecord` 的 ~335 行处，MVCC/非 MVCC 两条路共用）：

```cpp
// 通用 diff：扫 old/new 字节，合并出连续差异段（容忍 8B 内间隙以减少段数）
static int byte_diff(const char* a, const char* b, int n, DiffRange out[8]);
// 段数 ≤8 且增量总量 < 全行 2/3 → 写 UPDATE_DELTA；否则回退全量 UpdateLogRecord
```

### 2.2 恢复端（`log_recovery.cpp`）

- `PendingOp` 增加 `deltas` 变体；analyze 解析 UPDATE_DELTA 进 `uncommitted_`。
- **redo**（committed）：`fh->get_record(rid)` 读现行 → 逐段覆写 new bytes → `update_record`。字节段物理覆写，天然幂等。
  记录必存在：能被 update 的行其 insert 要么在检查点前（静态检查点全量落盘）、要么是更早的已提交日志（redo 按日志序先重放 insert 全量镜像）。防御性处理：不存在则跳过并记 stderr 警告（理论不可达）。
- **undo**（uncommitted）：同上逐段覆写 old bytes（写锁保证行存在）。
- 旧 `UpdateLogRecord` 路径原样保留（回退用 + 兼容跑到一半的旧日志——OJ 每次全新建库，无迁移问题）。

### 2.3 预期

| 记录 | 现状 | 瘦身后 |
|------|------|--------|
| stock update ×10 | ~6.8KB | ~0.7KB（28B 头 + 名 + 4 段×~14B） |
| district update | ~500B | ~70B |
| order_line insert ×10 等 | ~1.9KB | 不变（insert 必须全量） |
| **NewOrder 合计** | **~9-10KB** | **~2.7KB（-70%）** |

### 验收

`run_tests` 11/11；kill -9 恢复（重点：含 UPDATE_DELTA 的日志被 redo/undo 后 `bench_tpcc` 一致性检查全过）；`WAL_STATS` 的 bytes/batch 应降 ~60-70%；`--mid` A/B。

## P3：字节/等待者阈值组提交（条件启动，1 天）

**前置门槛**：仅当 P0 显示 `commit_waits/n_fsync ≤ 2`（聚合效率低）才做；若已 ≥4 则跳过（S5.2 的教训之一就是没先量批次效率）。

### 设计（与 S5.2 的本质区别：可被新请求即时打断，不死等）

```cpp
// flush_worker 换缓冲前：
// 高并发快路径：阈值已满足 → 零延迟立即刷（绝大多数批走这里）
// 低并发慢路径：cv_.wait_until(lock, first_req_time + T_max,
//        [&]{ return persist_waiters_ >= N || pending_bytes >= M
//                  || space_waiters_ > 0 || stop_; });
```

- `persist_waiters_`：atomic，`wait_for_persist` 慢路径进入 +1 / 醒来 −1（P0 已加计数，此处复用）。
- 每个新 committer 的 `request_flush` 本就 `cv_.notify_one()` → worker 立即醒、重查谓词 → **阈值一满足马上刷，无固定延迟**。只有「孤独 committer」才等到 `T_max` 超时——低并发时延迟换不来批次，代价可控且不乘在每笔 commit 上（这正是 S5.2 `sleep_for` 死等被判题机调度放大的失败点的反面）。
- 参数：`RMDB_GC_WAITERS`（默认 0=关）、`RMDB_GC_BYTES`、`RMDB_GC_DEADLINE_US`。**默认关**；本地用 P0 报表调参（看 commit_waits/fsync 是否上升、p99 是否恶化），OJ 上仍需独立 A/B——`wait_until` 超时路径在判题机同样有调度延迟风险，但它只在低并发批触发，损益结构与 S5.2 完全不同。
