## 以后怎么做（性能优化时顺带做）

### 原则

1. **随改随收**：只动**当前正在优化的文件/函数**里的注释，且尽量与逻辑改动同一次提交。
2. **小步 diff**：单次 PR / 提交里，注释变更控制在相关文件内；避免跨 10+ 文件纯注释提交。
3. **功能优先**：注释是人味化，**不能**替代正确性验证；改完仍要 `make rmdb` + 相关 local 测试。
4. **框架注释不动**：`@description` / `@brief` / lex-yacc 生成代码里的说明，除非改接口语义，否则别整段重写。

### 什么像「AI 写的」（以后慢慢删/改，不要一次删光）

| 特征 | 示例 | 建议 |
|------|------|------|
| 性能小论文 | `perf 实测占 87% CPU`、`OJ 从 53 拉到 799` | 删掉或留一句「删键索引，别全表扫」 |
| 分节横幅 | `/* -------- 题9：MVCC -------- */` | 去掉横幅，必要时一行说明 |
| 编号优化 | `优化 4：`、`Fast path：` | 改成普通中文或删掉 |
| 旧实现复盘 | `旧实现锁 64 分片…曾占 47%` | 只保留**现在**在做什么 |
| 箭头链 | `A → B → abort（安全）` | 改成短句 |
| 英文标签堆叠 | `O(1) 点查`、`hot path`、`semantic equivalent` | 能不用就不用 |

### 什么可以像人写的

- 一两行，说明**非显然**的坑：锁顺序、默认 SER 别改、district 计数器不能回退。
- 和变量名一致，不重复代码已表达的信息。
- 偶尔留 `TODO` / `FIXME`，但别写成长篇设计 doc。

### 推荐节奏（示例）

```
第 1 次优化 BPM     → 只改 buffer_pool_manager.* 里新增/碰到的注释
第 2 次优化 Payment → 只改 transaction_manager / executor_update 相关段落
…
```

每轮最多「顺手」改 5～15 行注释，而不是整个 `transaction_manager.cpp` 通改。

- **`src/` 会提交**：注释风格应自然、增量，避免单次巨大 stylistic diff。
- **`Docs/` 不会提交**：分析、火焰图、本备忘、OJ 记录放这里；Agent 开工前可先读 [0.优化索引](./0.优化索引.md) 和 [1.TPC-C性能优化分析](./1.TPC-C性能优化分析.md)。
