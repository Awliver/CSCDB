## 4. 🧊 已冻结 / 条件性实施计划

### P0-A：补齐 H3 — INLJ 的 SSI 内表读跟踪

**状态（2026-08-01）**：🧊 已实现并冻结。修前确定性 H3 会错误返回 join 行，修后当前 SELECT 返回 `TRANSACTION_ABORT` 且 T2 写回滚；H3/H3S、功能 11/11、SI W=5 mid（中位 4312.10）通过。随后 `bc2c208` 官方 25 功能、5 恢复、COMMIT 32/32、崩溃恢复和 I/O 诊断全 PASS。排名固定 SI，H3 的谓词/RID 跟踪只在 SER SELECT 启用；最新 34,592 不替换 37,248.4 性能锚点，也不构成回滚 H3 的因果证据。

**问题**：INLJ 内表已经按 MVCC 快照重建可见版本，但没有像 IndexScan 一样登记右表谓词和逐 RID 读，SER 危险结构可能漏边。

**实现**：

1. 为 `IndexNestedLoopJoinExecutor` 增加 `ser_on_`，仅在 `context_->ser_in_select_ && is_ser(txn)` 时启用。
2. 每次根据左行构造右表 lookup key 时，同时构造只引用右表列的实例化谓词；在 probe 前调用 `ser_record_pred` 与 `ser_read_pred_check`。
3. 对每个实际命中的右表 RID，在返回 join 行前调用 `ser_record_read` / `ser_read_check`；新形成危险结构时在当前语句立即抛 `TransactionAbortException`。
4. 不用“整表读”替代动态谓词；避免扩大冲突集和误 abort。

**冻结证据**：确定性三事务 dangerous-structure 在触发 SELECT 立即 `TRANSACTION_ABORT`；索引键移动场景强制覆盖实际 RID 读检查；SER join 并发、功能门禁、本地 SI mid 与官方完整门禁均通过。解冻条件仅为新的 SER Join 正确性反例，不因跨次排名噪声解冻。

### P0-B：补齐 H4 — `ser_finish` 的 active_rts 锁域

**状态（2026-08-02）**：🧊 已实现并冻结。`5ae93e4` 已通过官方 25 功能、5 恢复、COMMIT 32/32、W=50 装载、三轮排名、崩溃恢复和 I/O 诊断；排名中位 **33,862.8**，不替换性能锚点。

**问题**：`ser_finish` 在 `ser_latch_` 下读取 `active_rts_`，但该集合由 `rts_latch_` 保护。

**实现**：

1. commit/abort 在现有 `rts_latch_` 临界区内删除自己的 read_ts，并计算 `gc_watermark`。
2. 将 watermark 作为参数传给 `ser_finish`；`ser_finish` 不再直接读取 `active_rts_`。
3. 禁止同时嵌套持有 `rts_latch_` 与 `ser_latch_`，保持固定无嵌套顺序，避免引入 ABBA。

**冻结证据**：H4 由 smoke 升级为 16×200 SER 事务，连续 20 轮共 64,000 事务 PASS；TSan H4 PASS 且无 race；功能 11/11、C1/C2/H3/H4/H5 5/5 PASS。同提交同机 W=5 SI mid A/B 为 4,137.05 → 4,138.23（**+0.0285%**），满足 ±1% 门槛；随后 `5ae93e4` 官方完整门禁 PASS。解冻只接受新的 SER 正确性反例、TSan race、锁序问题，或同提交受控 SI A/B 退化超过 1%。

### P1-A：异常放弃率的事务族/语句/原因归因

**状态（2026-08-03）**：🧊 已实现并通过确定性闭环、完整正确性门禁、官方统计关闭态全流程和 W=5 单变量取证。两次 W=50 开启态分布因本机测试成本不可接受而不执行；该诊断不属于功能、恢复、持久化或排名门禁，不能据此宣称已确定异常 abort 根因。完整数字见 [§15](./15.P-A1归因取证.md)。

**实现**：

1. 内核用稳定 `AbortReason` 与 MVCC/锁内部结果枚举透传原因，不解析英文诊断文本；abort 时机、回滚、Wire 帧和状态码不变。
2. 服务端仅记录 `stmt_id × op_index × reason` 的 attempt/abort/耗时，每 5s 输出增量；未设置 `RMDB_STMT_STATS` 时不计时、不分配槽、不做原子计数。
3. 客户端将 `stmt_id/failed_op` 映射到事务族和热点，JSON 记录 attempted/committed/business rollback/abnormal abort/error，数据库内核不硬编码 TPC-C 名称。

**已有证据**：

- PA1 确定性用例验证 ACTIVE/STALE token、`failed_op`、AUTO_ABORT 清理、5s 输出及服务端/客户端 abort 精确对账。
- W=5 五进程/侧 A/B：OFF 中位 4,351.07，ON 4,349.29，变化 **-0.041%**；配对差值噪声范围 -6.08%～+3.02%，需在 W=50 复核。
- W=5 ON×5 测量窗共 15,431 次异常：STALE 81.82%、ACTIVE 18.18%；Top-3“事务×语句×原因”覆盖 **80.11%**，五次主原因占比极差 **4.00pp**；完整进程服务端/客户端 abort 总量 5/5 逐样本一致（合计 19,141）。
- `c446377` 官方 W=50 全流程 PASS、40,264.8；该报告为统计关闭态，只证明默认路径。

**冻结口径**：原退出条件为两次 W=50 形 30s+3×150s 取证、完整对账、Top-3 覆盖 ≥80%、两次占比差异 ≤10%、开启态开销 ≤1%；这些条件**未执行，不记为通过或失败**。默认保持 `RMDB_STMT_STATS` 关闭，不启动并发策略、PREPARE 或 WAL 实验。只有获得可接受的同规格资源且明确重新授权，才按原门槛恢复终验。

## 6. 统一验证方案

### 6.1 每个改动的固定顺序

1. **单变量提交**：一个 commit 只含一个机制；必须有运行时 A/B 开关或可直接回退的独立 commit。
2. **编译与功能**：Release 增量构建；`tests/run_tests.py`；完整 consistency（不能只跑 C1/C2/H5）。
3. **定向用例**：针对假设验证机制，不用总吞吐掩盖错误。
4. **W=5 趋势**：同机、同数据、同 CPU 配额，至少 5 个独立进程样本；比较 median、p99、abort 和 RSS 斜率。
5. **W=50 决赛形**：fresh load；30s+3×150s、32 客户端、SI、仓库 50/50；完整崩溃恢复与 I/O 诊断。
6. **上线判定**：正确性全绿后才看性能；任何 ERROR、恢复差异或不可解释漏行都直接判退。

### 6.2 量化门槛

| 类型 | 上线门槛 |
|------|----------|
| 吞吐优化 | W=50 形中位提升 **≥5%**；任一轮不得退化 >2% |
| 冲突优化 | 异常 abort 相对下降 **≥20%**，且吞吐不退化 >2% |
| 尾延迟优化 | 目标 batch p95/p99 至少下降 **20%/10%**，吞吐不退化 >2% |
| 内存优化 | 峰值 RSS 至少下降 **10%**，或消除正向 RSS 斜率；吞吐退化 ≤2% |
| 装载优化 | fresh W=50 仍 <900s，行数/索引/重启抽样全过 |
| 正确性修复 | 功能、SI/SER、恢复、FLOAT32、COMMIT 持久化全部 100% PASS；性能以不退化 >2% 为目标 |

低于门槛但方向正确的结果记为“无显著收益”，进入 🧊，不靠主观判断上线。
