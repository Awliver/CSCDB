## P0：删-插冲突检测按键索引化（预期收益最大，3-5×）

**问题**：`mvcc_insert_key_conflict`（transaction_manager.cpp）在每次 INSERT 时
持全部 64 分片锁、线性扫描该表**所有**版本链找同键删除冲突。链条目 ∝ 累计事务数。

已做的两道缓解都在真实负载下失效：
1. 删除活动门（`active_del_txns_ > 0` 才扫）：delivery 平均 754ms × 每秒 ~2 笔
   ⇒ 几乎任何时刻都有 delivery 在飞 ⇒ 门恒开；
2. 干净链 GC：8 客户端下水位 = min(活跃 read_ts) 恒低于刚提交版本
   ⇒ `hist[0].commit_ts > prune_wm` ⇒ 几乎从不回收 ⇒ 链继续累积。

**方案**：为"被删除过的键"建 per-table 哈希索引，插入时 O(1) 点查代替全扫：
```
per-table: unordered_map<key_bytes, DelEntry{ writer_txn, last_del_cts }>
- mvcc_write(is_delete):   登记 uncommitted 删除键（writer = 本事务）
- commit:                  转为 committed（记 cts），清 writer
- abort:                   移除本事务的 uncommitted 登记
- 惰性清理:                committed 且 cts <= 全局水位的条目可删
插入检查: 查自己首列 key —— 命中 uncommitted(他人) 或 committed 且 cts > 我的 rts → 冲突
```
语义比原全扫**略保守**（不再验证旧版本对本快照可见，误报只多 abort 不破坏正确性；
TPC-C 键单调递增，实际误报≈0）。集合天然小：只含被删过的键（TPC-C 只有 new_orders）。
改动集中：mvcc_write / commit / abort / mvcc_insert_key_conflict 四处 + 一个新 map。

## P1a：B+Tree 加锁算法（次大头，尾延迟主因之一）

**现状**：每索引一把 `root_latch_` 互斥锁（ix_index_handle.h:170）。
`get_value / insert_entry / delete_entry / lower_bound / upper_bound /
IxScan::next/is_end/rid` **每个操作**全树串行。这是修并发崩溃时的保守粗锁——
正确但把 8 客户端在热索引（stock/order_line）上排成队，直接制造 p99 尾巴。

**演进路径**（风险递增）：
1. **读写锁化**：`root_latch_` → `shared_mutex`，读操作（get_value/scan/bounds）共享、
   写独占。TPC-C 读多写多参半，预期缓解 30-50% 排队。改动小，先做。
2. **Latch crabbing**（教科书方案）：per-page 读写 latch，从根向下逐层加/放；
   写路径先乐观（只锁叶），分裂才回退悲观全路径。框架已有 page latch 位
   （Transaction::index_latch_page_set_ 就是为此准备的）。
3. **OLC（乐观锁耦合）**：节点版本号 + 读侧重试，写侧短锁。性能上限最高，
   实现/调试成本也最高，建议在 crabbing 稳定后再评估。

**配套必修**：`IxScan` 的定位式 `end_`（(page,slot) 对）在并发分裂下天然失效
（已用 header 页哨兵 + 逐行 eval 兜底，正确但多扫）。细锁化之前应改为
**携带上界 key**，每步用 `ix_compare(cur_key, upper_key)` 判断终止——同时消除
兜底带来的越界扫描。

## P1b：delivery 事务治理（abort 率 36% → 目标 <5%）

delivery 一个事务串行处理 10 个 district、每个都抢 new_orders 最老行 + district 行，
与 new_order/payment 冲突面大，wait-die 大量误杀（p50 598ms 也含锁等待）。

方向（按侵入度）：
1. **workload 侧**（tpccbench 可选项）：delivery 拆成每 district 一个事务
   （TPC-C 规范 2.7 允许 deferred execution，逐区提交合规）；
2. **引擎侧**：`select min(no_o_id)` 走索引首条读且不落谓词锁；
   district 行锁改为最后再拿（缩短持锁窗）。

## P2：其余方向（当前占比小，吞吐上去后会浮现）

| 方向 | 现状证据 | 建议 |
|---|---|---|
| **B+Tree 实现** | `binary_search = false`（节点内**线性查找**，ix_index_handle.h:18）；`fetch_node` 每次 `new IxNodeHandle`（堆分配） | 打开二分（改常量+验证）；NodeHandle 栈上化/复用 |
| **Buffer Pool** | fetch_page 仅 0.54% CPU；池 256MB 未满 | 暂缓。P0/P1 完成后重新 perf；届时按 Docs/Optimize/2,3 的分片+IO出锁方案推进 |
| **WAL/组提交** | commit 每笔 `wait_for_persist` 同步等待；组提交只有雏形 | 批量唤醒：后台 flush 线程按 N 笔/T 毫秒聚合 fsync，commit 等自己 lsn 落盘。降低 payment/new_order 尾延迟 |
| **MVCC 数据结构** | store 双层 map，外层 `string` 表名每次 hash；overlay key 用 `tab#rkey` **字符串拼接**（release_statement_writes 每语句执行） | 表名 → 表 id（int）；overlay key 改 (int,int64) pair |
| **锁管理器** | record_locks 无回收（Docs/Optimize/7 已立项） | 惰性回收 + 分片 |
| **解析器** | 未命中 fast-parse 的 SQL 走全局 yacc 锁（Docs/Optimize/5） | 对 TPC-C 影响小（热路径已覆盖），决赛 SQL 变体多时再处理 |

## 建议执行顺序

```
P0 删-插冲突键索引        ← 预期 tpmC 3-5×，改动集中，先做
P1a-1 root_latch_ 读写锁化 ← 半天，直接砍尾延迟
P1b delivery 治理          ← workload 侧一行配置 + 引擎侧小改
P1a-2 latch crabbing       ← 大头，做完 B+树不再是瓶颈
（重新 perf，再定 P2 顺序）
```

每步之后必跑：`tpccbench full --scale mini`（SI+SER）、`acid`、P2 官方 11 项、
全量 150s 曲线对比。正确性红线优先于任何性能收益。

### P0(SER)：ser_read_pred_check —— 47% CPU 的幻影检测（头号）
问题：每个 SER SELECT 在 beginTuple 调用它，内部 `MvccAllShardsGuard` **锁全部 64 分片**
（全局串行点）+ **线性扫整表版本存储**、逐版本 ser_record_matches。O(版本数)/次 且随
活动量增长。这也是 **OJ Join Test 43s→111s 回归的元凶**：NLJ 内表 beginTuple 每条外层
元组调一次 → O(外层×版本数)×全分片锁。
修复(分两步，风险递增)：
1. **门(低风险，仿 delete-key gate)**：每表维护 `active_writers` + `last_write_cts`；
   SER 读若"本表无活跃写者 且 last_write_cts <= 我的 read_ts" → 无幻影可能，整跳。
   TPC-C 中 item(从不写)/customer(几乎只读) 直接跳过，立省一大块；但热表
   (warehouse/district/stock)恒有写，门不触发。
2. **近期写索引(中风险，需题九验证)**：每表维护"未提交写 + commit_ts>水位的已提交写"
   小集合，ser_read_pred_check 只扫它、且不锁全分片 → O(并发写数)。热表也受益。
   必须验证不漏检幻影（题九 phantom 用例 + ssi_indexscan_verify）。

### P1(SER)：abort 率 43%（另一半吞吐）
6299 abort / 8261 commit——近一半事务做完被丢。SSI 在热行(warehouse w_ytd、district
d_next_o_id/d_ytd，被每笔 payment/new_order 触碰)上产生大量 rw 边 → 危险结构误判。
降低误报可直接抬高 committed tpmC，但**最易伤题九**(过松→漏检真异常)，需精细的
谓词/行粒度判定 + 充分回归。高收益高风险，放门优化之后。

### P2(SER)：低风险小win
- `si_overlay_key` 字符串拼接 → 改 (string,int64) pair 键或数值键（~2-4%）
- 外层 store map 表名 string → 表 id(int)（~2-3%）

### 建议顺序
P0-step1 门（安全，先做，顺带缓解 Join Test 回归）→ 重测 → P0-step2 近期写索引
（题九验证）→ P2 小win → 最后再碰 P1 abort 率（最谨慎）。

### 实施结果（2026-07-04 当日完成 step1+step2）
- **step1 门实测几乎无效**（perf 复测 ser_read_pred_check 仍 27.1%）：TPC-C 的读几乎
  全落在恒有在飞写者的热表上，门恒开；item 等只读表的 pred check 本来就是空扫
  （store 无该表条目），门只省了锁。教训：**预判"热表门不触发"时应同时预判读流量分布**。
  门保留（对只读表仍有锁节省，且是 step2 的前置快速路径）。
- **step2 近期写索引生效**：`recent_writes_[tab]`（写链 rkey 集合，写前登记、冷链惰性
  剔除，水位单调保证剔除安全），pred check 只扫该集合且不再锁全分片。
  perf：ser_read_pred_check 从 top **消失**；SER 满载 tpmC **3145 → 5240（+67%）**。
  正确性：SSI 等价性测试与改前逐项一致、mini SER/SI FULL PASS、ACID PASS、P2 11/11。
- **新的 top（下一轮目标）**：hashtable find 16.6%（mvcc_read 每行链查找）、
  `ser_write_check` 12.2% + ser_record_matches 12.3%（写方遍历全部 ser_ 条目 ×
  read_preds 匹配——读方修完后写方成为新瓶颈，同样的"只查相关"思路可治：谓词按表
  分桶，写方只匹配本表的谓词）、abort 率 43.6%（未动）。

### 第五轮（同日）：写方镜像反查索引 —— 5240 → 10856 tpmC（+107%）
`ser_write_check` 旧实现每次写遍历全部 ser_ 条目 × 线性扫其读集 × 按列名字符串
解析匹配谓词（perf 25%）。改为两个反查索引（均在 mvcc_meta_latch_ 下，与 ser_ 同生共死）：
- `ser_rid_readers_[tab][rkey]` → 读者集合：ser_record_read 登记，写时 O(1) 直查；
- `ser_pred_readers_[tab][txn]` → **预编译**谓词（record 时解析列偏移一次），写时只匹配本表；
- abort/GC 清 SerInfo 时经 ser_unindex 同步移除；编译失败（列不存在）＝旧语义"永不匹配"，不登记。
效果：两函数从 perf top 消失；tpmC 5240→**10856**；abort 43.6%→**28.5%**（事务变快
→重叠窗口变短→冲突自然减少）。验证：SSI 等价性逐项一致、mini SER/SI、ACID、delkey、P2 11/11。

### 当前 top（第六轮候选）
21.8% mvcc 链哈希查找 + 7.7% mvcc_read + 18% mutex —— 进入"每行 MVCC 开销"平坦区:
- SeqScan(SER 下范围查询仍强制) 每行 shard 锁 + 链查找：批量化/每页一次锁；
- 外层 store 表名 string → 表 id；si_overlay_key 字符串拼接 → pair 键；
- abort 率 28.5% 的剩余部分（热点行 SSI 误报——高收益高风险，最后做）。

### 第六轮（同日）：WAL 双缓冲组提交 —— 面向 OJ 慢盘的天花板
背景：OJ tpmC 1129 ≈ 43 事务/s，远低于本地满载 180+/s；本地涨 3.45× OJ 只涨 1.46×
——OJ 已被非 CPU 因素封顶。log_manager 旧实现 write+fsync 全在全局 latch_ 内：
fsync 期间（慢盘 5-20ms）**所有日志追加被锁死**，每笔 commit 实付一次 fsync，
吞吐上限 = 1/fsync 延迟——与 OJ 的 43/s 吻合。
改法（log_manager 双缓冲，~46 行）：worker 换出 active 后在**锁外** write+fsync；
fsync 期间新日志进新 active 排队——**fsync 时长天然成为聚合窗口**，一次 fsync 覆盖
一批 commit，组提交自然发生（无人为延迟窗口）。commit ACK 仍严格等待自身 LSN 持久。
验证：定向 crash 测试（4 客户端并发提交随机时刻 kill -9 × 4 轮，**41,600 笔已 ACK
提交零丢失**）、ACID D1、mini SER/SI、delkey、SSI 等价、P2 11/11。
本地 NVMe 也白赚 +17.6%（10856 → **12762** tpmC，fsync 期间日志追加不再停）；
OJ 慢盘预期收益显著更大（理论上限 ≈ 并发客户端数×）。

### 第六轮补丁 + OJ 诊断结论（组提交上线后 OJ 1129→1013，-10%）
负结果证伪了 fsync 封顶假设，同时暴露实现缺陷并给出关键诊断：
1. **缺陷修复**：排空循环曾无差别刷盘（无人等待也 fsync 语句日志）→ 后台连续 fsync
   在慢盘上抢占数据页 IO（Join Test 8.0→11.3s 同源）。改为**仅按需刷**：
   `requested_lsn_`（被等待的最大 lsn）+ `space_waiters_`，无人等待不 fsync。
   验证：crash 定向 4 轮零丢失、ACID、mini SER、P2 11/11；本地 11952 tpmC（无回退）。
2. **OJ 天花板模型**：53→773→1129→1013 是渐近饱和曲线 ⇒ OJ 客户端大概率为
   节奏(think-time)驱动的固定终端数，tpmC 上限 ~1000-1100 由终端数决定；
   引擎响应时间已远小于终端周期，纯吞吐优化不再推得动。
3. **推论——OJ 剩余最大杠杆是 abort 率（本地 24.9%）**：节奏驱动下每笔被 abort 的
   NewOrder 白烧一个终端周期，直接从 committed 里扣。降 abort ≈ 等比例抬 tpmC，
   且不依赖天花板模型是否精确成立（吞吐驱动下同样受益）。
   风险：SSI 危险结构判定精化最易伤题九，需最严格回归（phantom/等价性/全套）。
