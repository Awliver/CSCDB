## 2. 方案 B：算术增量热行（原 Payment YTD，已泛化）

### 子项

| 子项 | 内容 | SI 安全条件 |
|:--:|------|-------------|
| **B1** | 单列 `col=col±字面量`：`detect_col_arith_delta` + `mvcc_write_col_delta` | 写写 rebase 到 `hist.back()` |
| **B2** | commit 后链压缩；`watermark >= cts` 时可摘链（全表） | 有旧快照读者时不激进折叠 |
| **B3** | `mvcc_read`：`read_ts >= 最新 commit_ts` 时直读堆（全表） | 未提交写仍在 `writer_data` |

未做：**B4** YTD 内存累加器（recovery 风险高）。

### 命中的 SQL（`tpcc_transactions.py`）

仅 **Payment**（mix 10/23）：

```sql
update warehouse set w_ytd = w_ytd + ? where w_id = 1;
update district set d_ytd = d_ytd + ? where d_w_id = 1 and d_id = ?;
```

每笔 Payment ~9 条 SQL，其中 **2 条**走 B1；NewOrder **不计入 tpmC**，且主路径是 `update district set d_next_o_id`、多轮 `update stock`、大量 `insert`。

### 与 NewOrder 的锁关系

- NewOrder：`update district` 后持 **district 行锁直到 commit**（中间 5–15 轮 stock）。
- Payment：同一条 district 行改 `d_ytd`，与 NewOrder **争锁**。
- B 缩短 Payment 写 MVCC 开销，**不缩短 NewOrder 持锁时间** → 对 tpmC 间接收益有限。

### 验证（2026-07-06）

- `bench_tpcc.py --quick`：tpmC ~790，CONSISTENCY PASS  
- `stress_consistency.py`：4 trial PASS  
- `tests/run_tests.py`：11/11 PASS

## 4. tpmC 与 SQL  workload 对照

### 计分口径

**tpmC = 每分钟成功 commit 的 NewOrder 笔数**。Payment / OrderStatus 等再快也不直接加分，仅通过争用资源拖慢 NewOrder。

### 事务 mix（OJ / `bench_tpcc.py`）

10/23 NewOrder · 10/23 Payment · 各 1/23 OrderStatus / Delivery / StockLevel

### 按语句数加权的热路径（NewOrder）

| SQL 模式 | 次数/笔 | 当前优化覆盖 |
|----------|:--:|--------------|
| `update district set d_next_o_id` | 1 | **S1** `col_delta` 绝对 int（profile **~9%**，原 ~31%） |
| `update stock set …` | 5–15 | **多列 patch**（`mvcc_write_col_patch`） |
| `insert order_line` / `orders` / `new_orders` | 2 + 5–15 | 索引 + WAL（profile 各 <1%/步） |
| `select stock` / `item` | 5–15 | C3 索引读 rwlock |

### 优化收益排序（对 tpmC，2026-07-08 修订）

1. ~~锁 abort 税（wait-die）~~ → **WFG 已解决**（full scale NewOrder 0 abort）  
2. ~~district 整行 MVCC~~ → **S1 `col_delta` 已解决**（update_district **~31% → ~9%**）  
3. ~~district 锁与 fsync 重叠~~ → **S3 unlock→fsync 已解决**（本地 tpmC **~770 → ~1900+**）  
4. **commit / WAL**（S3 后 profile **~70%**，下一刀 **[S5](./4.S5-WAL组提交深化.md)**）  
5. 磁盘 I/O、evict 冷路径（perf kernel read 天花板 → **S6**）  
6. insert 叶页 pin 加强（**S7**，边际次于 S5/S6）

## 8. WFG 死锁检测与 2026-07-07 profile 复测

### 背景

wait-die 补丁（年轻事务遇锁即 `return false`）在 mini 8 线程下 NewOrder abort **~87%**，tpmC 从 ~1200 回落至 ~400 量级。OJ 仍 AC，但性能受损。

### 实现

| 模块 | 变更 |
|------|------|
| `lock_manager.cpp` | wait-for 图；成环时 abort **txn_id 最大**者；`wait_for(1ms)` + `lock_abort_` 兜底 |
| `transaction.h` | `lock_abort_` atomic；`request_lock_abort()` / `lock_abort_requested()` |
| `executor_update.h` | stock 多列 `SET` 走 `mvcc_write_col_patch`（与 WFG 同期） |

### 本地实测（Release，full scale W=1，8 线程）

| 命令 | 结果 |
|------|------|
| `bench_txn_profile.py --scale full --txn new_order -i 30 -t 8` | **30/0**；commit **51.6%**，update_district **30.5%**，stock 各 **<1%** |
| `bench_tpcc.py --quick --threads 8` | tpmC **793.49**；NewOrder **204/0**；CONSISTENCY PASS |
| `profile_tpcc.sh --measure 60` | `20260707_151828`；perf 下 tpmC **654.86**；kernel read **~26%**，`cond_timedwait` **~6.4%**，write **~6.3%** |
| `repro_stock_lock_deadlock.py` | 一 commit 一 abort，**<0.1s** |

### 结论

- **abort 矛盾已解**：WFG 后 full scale NewOrder **0 fail**，tpmC 回到 OJ **~800 平台**（非 ~1300）。  
- **冲更高分**需打成功路径：**commit + district + 磁盘 I/O**；WFG 的 1ms 轮询有 **~6%** 副作用待收。

## 12. S5.1/S6/S7.1 落地（2026-07-08，`1b4e421`）

> Git：`1b4e421`「锁拆分 + BPM evict分片」— 6 文件（`log_manager`、`buffer_pool_manager`、`ix_index_handle`）。

### S5.1：`log_manager` 锁拆分

`add_log_to_buffer`（写缓冲）与 `wait_for_persist`/`flush_log_to_disk`（等持久化）拆成 `append_mtx_` / `persist_mtx_` 两把锁，不再共用一把 `latch_`；`flush_worker` 摘缓冲用前者、改 `persist_lsn_`/`requested_lsn_` 用后者，两把锁不嵌套持有，避免和 committer 互相等待。详见 [§4 §0.1](./4.S5-WAL组提交深化.md#01-s51-锁拆分落地2026-07-08)。本身不直接压 commit 占比（仍 ~70%），主要是给 S6/S7 腾并发空间。

### S6：BPM evict 分片（方案 A）

`BpmShard` 新增按 `frame_id % BPM_NSHARDS` 静态划分的 `free_frames_`，去掉全局 `free_list_` 和 `evict_latch_`。`reserve_victim_nolock` 从 `pref_shard` 起逐分片找帧（先看本分片 `free_frames_`，再看本分片 `replacer_`），全程一次只碰一个分片的锁；`fetch_page` 冷路径的"查重 + 占坑"合并到本分片 `inflight_mtx_` 一次临界区内，`reserve_victim_nolock` 调用挪到锁外（避免和跨分片扫描产生 ABBA）。

### S7.1：索引叶页 pin 持有

`IxIndexHandle` 新增 `pinned_leaf_no_`/`pinned_leaf_page_`：顺序插入命中同一叶且这页的 pin 还攥着时，直接复用已有 `Page*`，连 `fetch_node`/`unpin_page` 都不调；换叶、分裂、`delete_entry`、析构都会正确放掉旧 pin（`release_pinned_leaf()`），避免和 `coalesce`/`redistribute` 冲突。

## 16. S5.2 上线回退（2026-07-09 晚）

**事实**：把 §15 的默认 80μs 版本上线后，OJ tpmC 从 S5.1+S6+S7.1 的 **~950** 掉到 **~800**，几乎回到 2026-07-05 最初基线 799.83。与本地 30s+360s×3 A/B 测出的「−0.87%，噪声内」中性结论**直接矛盾**。

### 根因推断

`flush_worker` 的 `first_round` 微批门槛（有 committer 在等 + `space_waiters_==0`）在正常负载下**几乎每个刷盘批次都会触发一次**——也就是几乎每次 commit 都要走一次 `std::this_thread::sleep_for(80us)`。本机是低负载独占裸机，`sleep_for` 唤醒延迟贴近请求值；但 `nanosleep`/`sleep_for` 的**实际**唤醒精度高度依赖内核调度器状态——虚拟化、共享 vCPU、或线程数远超核数时，睡眠到期后线程要等下一次真正被换上 CPU 才能继续，这个延迟可以是几百微秒到毫秒级，比请求的 80μs 大一个数量级以上。OJ 判题机大概率是这种环境（多客户端线程 + 服务端多线程共享有限核数），等于**几乎每次 commit 都被多加了一次不可控、可能达毫秒级的调度延迟**，直接拉长 commit 墙钟。

### 已执行的止损

`log_manager.h` 的 `group_commit_window_us_` 默认值改回 **`0`（关闭）**；`RMDB_GROUP_COMMIT_WINDOW_US` 环境变量机制保留，仅供本地/未来受控实验，不再默认生效。已重新编译（`rm bin/rmdb && make rmdb`），`run_tests.py` 11/11 PASS 确认回退无副作用；commit `9726c6a` 已 push 到 `gitee`（OJ 拉取的仓库）。

### 回退效果确认（2026-07-10）

线上复测 **tpmC 显著回升**（用户反馈），验证了"`sleep_for(80us)` 在 OJ 判题机上的实际调度唤醒延迟远超本机裸机环境"这一根因推断。这次事故走完了完整的「上线退化 → 诊断 → 回退 → 线上验证」闭环，佐证了下面"教训"部分的判断是对的，不只是猜测。

### 教训

1. **本机裸机测出的"中性/无回归"不能代表 OJ 判题机的调度行为**——尤其涉及微秒级 `sleep_for`/`usleep`/自旋等待这类对调度延迟极度敏感的机制，本机是最乐观情形，不是有代表性的下限。上线前应先用更贴近 OJ 特征的环境（限核 cgroup、`taskset` 绑核到少于线程数的核心、或容器化）复测一次调度延迟敏感的改动。
2. 硬编码非零默认值这个决策本身不是问题（不依赖环境变量注入确实是对的），错在**没有先验证"固定时长 sleep"这个机制在高并发抢核场景下是否安全**就直接上线成默认值。
3. 若后续要重新尝试 S5.2，换一种对调度延迟不敏感的触发机制——比如**已到达的 committer 数量 / 累计字节数阈值**（§4 §2.A 提到的「字节 / 等待者阈值」S5.2+ 方向）而不是固定 sleep 时长；或者把窗口设计成"能被新请求立即打断提前结束"而非死等固定时长，避免调度延迟被无差别放大到每一次 commit 上。
