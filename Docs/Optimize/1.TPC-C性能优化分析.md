## 1. 锁的粒度调整优化

### 1.1 现状评价（方向正确）

- **热行用 per-record 锁**：`district`/`warehouse`（TPC-C 高冲突单行表）的更新走 `lock_exclusive_on_record`（`executor_update.h:99-102`），其余走 MVCC。把强一致需求集中到最热的几行，避免表锁，思路正确。
- **表级锁全是 no-op**（`lock_manager.cpp:63-103` 直接 `return true`）：无表锁开销，靠 MVCC 做隔离，对 TPC-C 合理。
- **MVCC 存储已 64 分片 + 每分片独立数据**（`MVCC_NSHARDS=64`，`mvcc_shard_data_[64]`，`transaction_manager.h:255-267`）：`(tab,rkey)` 经 `mvcc_shard_idx` 固定映射到唯一分片的 `{store,pending}`，读写只抢该分片锁——并发设计良好，且消除了旧版"同表不同 rkey 共享内层 map"的结构竞争（见 §1.5）。
- 事务 id/ts 已用 `std::atomic`（`transaction_manager.h:244-245`），begin 的 `latch_` 仅保护 `txn_map` 插入。

### 1.2 ✅ 已做（原 🟠 P1）：commit 的全分片屏障已消除

**现状（2026-06-26）**：`commit` 已**去掉 `MvccAllShardsGuard`**，改为按本事务 `write_set` 逐条加 per-shard 锁并提交版本（`transaction_manager.cpp:250-285`），仅在末尾用 `mvcc_dirty_mutex_` 把 `touched_tabs` 写入 `mvcc_dirty_`（`:289-292`）。提交点不再锁全部 64 分片。

> **澄清（2026-07-06 修订）**：`prune_mvcc_after_commit` 已启用常规水位剪枝 + **warehouse/district 热行**在 `watermark >= cts` 时的摘链/单版本折叠（方案 B2）。仍须在 SI 下保留旧快照读者所需的中间版本。

### 1.3 ✅ 已做（2026-07-06）：`mvcc_meta_latch_` 拆为 `rts_latch_` + `ser_latch_`

**现状**：`mvcc_meta_latch_` 已删除。`active_rts_` 由 `rts_latch_` 保护；`ser_` 图由 `ser_latch_` 保护；`last_commit_ts_` 在 commit 用 `fetch_add`。SI 路径 commit **不再抢 `ser_latch_`**。详见 [§5 方案 C](./5.已完成优化摘要.md#方案-cmeta-拆锁--overlay--b-rwlock2026-07-06)、[§3](./3.方案A-C优化记录与tpmC评估.md)。

**历史（2026-06-27）**：`table_is_dirty` 已拆出 `mvcc_dirty_mutex_`。

### 1.4 ❌ 未做（🟢 P3）：`record_locks_` 无限增长

`get_record_lock`（`lock_manager.cpp`）仍为每个触及 rid 建 entry 且从不回收；`unlock` 只清 `lock_set` 不删 map 项。WFG 后等待方增多但 district/warehouse 行数仍有限，低优先级。

### 1.5 ✅ 已做（2026-07-07）：WFG 死锁检测（替代 wait-die）

**问题**：stock 行锁顺序由客户端随机 `i_id` 决定，wait-die 使年轻事务遇锁即 die；mini 8 线程 NewOrder abort **~87%**，tpmC 大幅回落。

**做法**：`lock_manager.cpp` 维护 wait-for 图；成环时只 abort **txn_id 最大**（最年轻）事务；其余继续等锁。牺牲者经 `Transaction::lock_abort_` 标记。**S2**：等待改为 `cv.wait`（去掉 1ms 轮询）。

**验证**：见 [§3 §8](./3.方案A-C优化记录与tpmC评估.md#8-wfg-死锁检测与-2026-07-07-profile复测)（WFG）与 [§3 §10](./3.方案A-C优化记录与tpmC评估.md#10-s1s3-落地2026-07-08)（S2）。

### 1.6 ✅ 已做（2026-06-27）：MVCC store 分片数据归属（正确性 + 并发）

**问题**：旧版 `mvcc_store_` / `pending_si_writes_` 为全局 `map<tab, map<rkey, …>>`，分片锁按 `(tab,rkey)` 哈希，但**同表不同 rkey 会落到不同分片锁、却并发改写同一个内层 `unordered_map`**（插入新 key 触发 rehash）。高并发 SI abort 路径（`restore_writers_from_overlays`）曾因此 SIGSEGV；缓冲池 Replacer 分片后吞吐升高，该 latent race 被放大暴露。

**修复**：改为 `std::array<MvccShardData, 64> mvcc_shard_data_`，每分片独立 `{store, pending}`（`transaction_manager.h:263-267`）。单记录操作只访问 `mvcc_shard_data_[mvcc_shard_idx(tab,rkey)]`；全表扫描（`mvcc_insert_key_conflict`、`ser_read_pred_check`）在 `MvccAllShardsGuard` 下逐分片迭代。

**验证**：`unit_test` BufferPool 3/3 PASS；`bench_tpcc.py --quick` 8 线程 **tpmC ≈ 480，CONSISTENCY PASS**（不再 Connection reset / SIGSEGV）。

## 2. 缓冲池大小与刷盘策略

### 2.1 ✅ 已做（原 🔴 P0）：缓冲池 latch — I/O 移出 + page_table_ + Replacer 分片

**已做（I/O 移出锁，✅）**：`fetch_page` 已重构为：持分片锁选 victim、预占 frame 并标记 `frame_io_inflight_` / `page_io_inflight_`，**释放锁后**再做 `write_page`（脏 victim）+ `read_page`（缺页），完成后重抢锁登记；并发命中同一在途 page/frame 用 `io_cv_` / `inflight_cv_` 等待。

**已做（page_table_ + Replacer 分片，✅）**：`BpmShard` 64 分片，每分片独立 `latch_` + `page_table_` + **`replacer_`**（`buffer_pool_manager.h:34-43`）。类级 `page_table_`（`:47`）为题一接口保留字段，**运行时未使用**，查找均走 `shards_[i].page_table_`。

```34:54:src/storage/buffer_pool_manager.h
    struct BpmShard {
        std::mutex latch_;                  // 保护 page_table_ + 本分片 replacer_ 的成员关系
        ...
        std::unique_ptr<Replacer> replacer_;
        std::deque<frame_id_t> free_frames_;  // S6：按 frame_id%N 静态划分，无全局 evict_latch_
    };
    ...
    std::unordered_map<PageId, frame_id_t, PageIdHash> page_table_; // 题一接口保留（运行时未用）
    std::array<BpmShard, BPM_NSHARDS> shards_;
```

**不变式**：帧在 `shard[s].replacer_` 中 ⟺ 承载 `hash(page)%64==s` 的页且 `pin_count==0`；所有 replacer 增删（pin/unpin/victim）在**本分片 `latch_` 下**完成。

**热路径（无全局锁）**：
- `fetch_page` 命中且已 pin：只增 `pin_count_`。
- `fetch_page` 命中但 `pin_count==0`：分片锁内 `replacer_->pin` + 增 pin。
- `unpin_page`：`pin_count→0` 时分片锁内 `replacer_->unpin`。

**冷路径（S6 后）**：缺页 / `new_page` 经 `reserve_victim_nolock`——优先本分片 `free_frames_`，再跨分片 `replacer_->victim()`，无全局 `evict_latch_`。详见 [§5 S6](./5.已完成优化摘要.md)。

**验证**：`unit_test` SampleTest（pool=10 精确容量/LRU）+ ConcurrencyTest（pool=50，5 线程×50 轮）PASS；`bench_tpcc.py --quick` CONSISTENCY PASS。

> 约束提醒：题目一规定"不可修改已有接口和数据结构变量"。分片化属于**内部实现重构**，对外接口 `fetch_page/unpin_page/...` 签名保持不变即可；`page_table_` 题一保留字段未删。

### 2.2 ✅ 已做（原 🟡 P2）：缓冲池大小

`config.h:39` 已上调为 `BUFFER_POOL_SIZE = 262144`（1GB），原 256MB 选项已注释保留。线上 RSS 仅 0.44GB，1GB 容量对 W=1 工作集充裕。

> 仍可做：若评测仓库数增大导致工作集超 1GB，再结合 `tests/prof` 火焰图/`perf stat` 复核缺页率后按需上调。

### 2.3 ✅ 已做（2026-07-05）：后台 page cleaner

`buffer_pool_manager` 的 `cleaner_thread_`：`free_frames_` 低于 `pool_size_/16` 时刷 `pin==0` 脏页。详见 [§5](./5.已完成优化摘要.md)。

### 2.4 ✅ 已做：双缓冲组提交 + append/persist 分锁

`LogManager`：`flush_worker` 换出 `bufs_[active_]` 后在**锁外** `write_log` + `sync_log`（`fdatasync`）；`append_mtx_` 与 `persist_mtx_` 已拆。无人等待 `requested_lsn_` 时不强刷，避免后台连续 fsync 抢盘。commit：`add_log` →（S3）`unlock_all` → `wait_for_persist(lsn)`。

**下一刀**：commit 墙钟暂无已验证方案；S5.2 固定 `sleep_for` OJ 负收益已搁置 → [§4](./4.S5-WAL组提交深化.md)。

### 2.5 ✅ 已修：淘汰路径 WAL 顺序

脏页落盘前均先 `g_log_manager->flush_log_to_disk()`（`fetch_page` / `new_page` / `flush_*` / cleaner）。

## 3. 线程模型与进程模型的权衡

### 3.1 现状：thread-per-connection + 全局解析锁

```608:610:src/rmdb.cpp
        pthread_mutex_lock(buffer_mutex);
        YY_BUFFER_STATE buf = yy_scan_string(stmt);
        if (yyparse() == 0) { ... }
```

flex/bison 默认非重入，用全局 `buffer_mutex` 串行整个 parse。团队已用**手写 fast-parse**（`try_fast_parse_sql`，`rmdb.cpp:334-340`）绕过它覆盖 insert/update/select/txn/delete 热路径——非常对路。另有 **`parse_set_isolation`**（`:64-76`）、**`try_parse_load`**（`:406-432`）、**`parse_set_output_file_off`** 不进 yacc。

### 3.2 ⚠️ 部分（原 🔴 P0）：fast-parse 已扩展，但解析器仍未重入

**已做（治标路线，✅）**：fast-parse 已覆盖 **DELETE**（`rmdb.cpp:320-329`）、**SELECT + ORDER BY + LIMIT**（`:250-265`）、update/insert/txn/select；`try_fast_parse_sql`（`:334-340`）依次尝试。TPC-C 四类主事务（NewOrder/Payment/OrderStatus/Delivery）**无 join**；**Stock-Level 含 `order_line, stock` 隐式 join**（已 INLJ，见 [§5](./5.已完成优化摘要.md)）。

**未做（治本路线，❌）**：解析器仍非重入，`buffer_mutex` 仍守着 yacc 回退路径（`rmdb.cpp:609-673`）。落不到 fast-parse 的语句（**CREATE INDEX、EXPLAIN、P2 功能测试中的复杂 SQL** 等）**多终端下仍被全局串行**——对 tpmC 影响有限，但对装载/功能测试并发有影响。

**仍可做**：让解析器重入（flex `%option reentrant` + bison `%define api.pure`），彻底删掉 `buffer_mutex`。当前命中率已高，优先级可视火焰图回退占比再定。

### 3.3 进程 vs 线程结论

对**单机 TPC-C**，多线程共享一个缓冲池是正确选择；多进程需共享内存且会牺牲缓冲利用率，**不建议改进程模型**。精力应放在"消除共享状态竞争"（第 1、2 节的分片化）。

### 3.4 ❌ 未做（🟢 P3）：其它线程层小问题

- 每连接 `pthread_create`（`rmdb.cpp:771`）可换**线程池**；TPC-C 连接长生命周期，收益有限，优先级低。
- ✅ **（2026-06-27）已修**：`client_handler` 的 `data_send` 原为 `new char[BUFFER_LENGTH]` 从不 `delete[]`（连接退出泄漏），现改为 RAII `std::vector<char>`（`rmdb.cpp:445-446`），随线程退出自动释放。
- ✅ **已做**：`SO_SNDBUF` 扩至 16MB（`rmdb.cpp:764-767`），装载阶段防发送阻塞。

## 4. 查询优化

### 4.1 现状评价（执行器侧扎实）

`SeqScanExecutor` 做得好：条件预编译（`compiled_`，避免逐行 `find_if`）、跨记录复用 page handle（`cached_page_`）、表未脏时跳过 MVCC 重建（`mvcc_on_`）。`insert_record` 有 page 缓存（`rm_file_handle.cpp:44-88`）。**同类 page 复用**也存在于 `executor_update.h`、`executor_delete.h`、`executor_index_scan.h`。B+ 树顺序追加插入有 `cached_leaf_no_` 叶页缓存（`ix_index_handle.cpp`）。

### 4.2 ⚠️ 部分（原 🟠 P1）：每次扫描调 `table_is_dirty`

```204:204:src/execution/executor_seq_scan.h
        mvcc_on_ = context_ && context_->txn_mgr_ && context_->txn_ &&
                   context_->txn_mgr_->table_is_dirty(tab_name_);
```

**已缓解**：`table_is_dirty`（`transaction_manager.cpp:775-778`）现在是 `any_mvcc_dirty_` 原子快路径 +（脏时）集合 `count`——**不再扫版本链**。

**（2026-06-27）已进一步优化**：原先脏态后每次扫描都抢全局 `mvcc_meta_latch_`（与 SER/`active_rts_` 共用）；现 `mvcc_dirty_` 已迁到专用 `std::shared_mutex mvcc_dirty_mutex_`，`table_is_dirty` 走**共享锁**，并发扫描互不阻塞，且不再与 SER 提交序维护争锁。鉴于 `mvcc_dirty_` 集合"只增不减"，共享锁读 + 偶发独占锁写的代价已很低。

**仍可做（可选）**：若火焰图仍显示该共享锁可见占比，可再改 per-table 原子标志做到读路径完全无锁。

### 4.3 缺乏代价/连接序优化

planner 的 join 顺序按书写顺序（`planner.cpp`），无 cost-based reorder。对 TPC-C 须**确保 NLJ 内表走 IndexScan（INLJ）**而非全表。`get_index_cols` 已支持最左匹配（`planner.cpp:28,67`），但要**逐条事务用 `EXPLAIN` 核对**访问路径：stock 按 `(w_id,i_id)`、customer 按 `(w_id,d_id,c_id)`、order_line 范围等是否都建索引并被选中。

### 4.4 ⚠️ 待外部验证：SER 路径极重 + 隔离级别确认

`ser_read_pred_check`（`transaction_manager.cpp`，`MvccAllShardsGuard` 下逐分片扫 `mvcc_shard_data_`）锁全部分片并扫整表版本链，每条 SER select 都付。`rmdb.cpp:451-454` **会话默认隔离级别仍是 SERIALIZABLE**（注释明确为题九 SSI 危险结构检测刻意保留，勿改默认）。

**改进**：**务必确认 TPC-C 基准用 SI 跑**（评测客户端发 `SET TRANSACTION ISOLATION LEVEL SNAPSHOT ISOLATION`），否则 SER 谓词跟踪会吃掉大量吞吐。

**仓库内可确认**：本地基准脚本已显式设 SI——`tests/local/tpcc_common.py:207`（bootstrap）、`tests/local/bench_tpcc.py:101`（每 worker）。未发 `SET TRANSACTION` 的新连接仍以 **SER** 运行；OJ 官方客户端是否设 SI 需对照评测端，代码层无法单独断定。

## 6. 验证与防回归

每次优化后**必须**保证正确性不退化：

```bash
# 1) 增量编译
cd build && make rmdb -j$(nproc)

# 2) 功能回归（先杀残留进程，避免 Bind error）
ps aux | grep "[r]mdb" | awk '{print $2}' | xargs -r kill -9
python3 tests/run_tests.py                       # P2 功能
python3 tests/local/bench_tpcc.py --quick        # 加载 + 8 线程 smoke/warmup/measure + 一致性
tests/prof/profile_tpcc.sh --quick               # → build/prof_out/<ts>/flamegraph.svg
tests/prof/perf_stat_tpcc.sh --quick
```

**优化纪律**：
- 一次只动一个瓶颈点，改完先跑功能回归再跑性能，确认"正确性不退、tpmC 上升"再进下一项。
- 涉及并发的改动（缓冲池分片、锁拆分）优先用 ASAN/TSan 编译跑一遍回归（见 AGENTS.md 调试速查）。
- 隔离级别默认值（SER）影响题九 SSI 危险结构检测，**不要为性能擅自改默认隔离级别**（见 `rmdb.cpp:408-411` 注释）。
