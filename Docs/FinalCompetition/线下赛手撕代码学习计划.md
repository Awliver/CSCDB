# 线下赛手撕代码学习计划

> **制定日期**：2026-08-03  
> **目的**：在不依赖 AI 的前提下，能够定位线下题的影响范围、读懂相邻实现、完成最小改动，并用测试证明改动正确。  
> **原则**：不追求逐行背诵全仓库；追求对四条关键链路做到“能讲清、能跟踪、能改动、能验证”。以当前已通过门禁的代码为学习基线，训练期间不开展性能重构。

---

## 0. 使用方式与每日节奏

### 每次学习的固定闭环（90–120 分钟）

```text
选一个具体行为和一条最小 SQL / 用例
  → 先预测它会经过的类和函数
  → 对照调用链文档定位，阅读入口与终点
  → 用断点或临时日志跟一遍正常路径
  → 写出“输入—状态变化—输出—失败边界”摘要
  → 做一个微小、可回退的改动或手写定向用例
  → 编译并运行定向测试，删除调试痕迹
```

不要连续“只读代码”超过 45 分钟。读不懂时先回答下面五题，再继续下钻：

1. 这个函数的输入、输出和副作用分别是什么？
2. 调用它之前，哪些条件必须成立？返回后，哪些状态必须成立？
3. 成功路径调用了谁；错误/abort 路径又回到哪里？
4. 它持有哪些资源（页 pin、锁、事务状态、日志缓冲），谁负责释放？
5. 用哪条现有或新建的测试能证明我理解的行为？

### 每日交付物（写在自己的笔记或本计划末尾的学习日志中）

- 一张不超过 10 个节点的调用链图；
- 3 个关键函数的“一句话职责 + 一个不变量”；
- 一条能复现正常行为的最小 SQL/脚本；
- 一个自己发现的边界条件或错误路径；
- 一个仍未理解的问题，并标注下一步要读的文件。

训练时可用本仓库已有的文档和测试；现场按比赛规则完全脱离 AI。临时日志只能放在 `.cursor/` 等忽略目录，验证后删除，不能带入提交。

## 1. 方向一：查询执行、记录与索引

```text
Parser → AST → Analyze(Query) → Planner(Plan) → Portal(Executor) → Record / Index → 输出
```

并能判断改动只在查询层，还是必须同步维护记录、索引、事务写集。

### 阅读顺序（先链路，后实现）

4. `src/analyze/analyze.cpp`、`src/optimizer/planner.cpp`、`src/portal.h`：只沿一条 SQL 所涉及的分支阅读。
5. `src/execution/executor_*.h`：先读基类，再读 `SeqScan`、`Projection`、`Insert`、`Update`、`Delete` 的 `beginTuple/Next`。
6. [`6b.存储与索引调用链`](../Analysis/ProjectAnalysis/6b.存储与索引调用链.md)：随后下钻 `RmFileHandle`、`RmScan`、`IxIndexHandle` 和 `IxScan`。

### 六次练习（每次只完成一项）

| 次序 | 最小场景 | 必须说清的内容 | 验收 |
|---|---|---|---|
| Q1 | `CREATE TABLE` + `INSERT` 一行 | 表元数据、记录写入、索引维护、write set 分别在哪发生 | 能从 SQL 跟到 `Rid` 返回 |
| Q2 | 单表 `SELECT ... WHERE` | 条件何时转换、扫描如何迭代、过滤在哪里发生 | 用断点/日志记录连续两次 `Next()` |

## 2. 方向二：事务、锁与 MVCC/SSI

### 掌握目标

能准确区分“锁解决什么、MVCC 解决什么、SI/SER 何时 abort”，并能沿一条事务解释状态变化、读写集/undo、锁和版本的生命周期。这个方向优先练**正确性**，不要为了性能调整并发语义。

### 阅读顺序

1. [`6c.事务恢复调用链`](../Analysis/ProjectAnalysis/6c.事务恢复调用链.md) 的事务、MVCC+SSI 两节。
2. `src/transaction/transaction.h`、`txn_defs.h`：先认清 `Transaction` 的状态、write set、lock set、undo log。
3. `src/transaction/transaction_manager.{h,cpp}`：按 `begin → commit / abort` 顺序读。
4. `src/transaction/concurrency/lock_manager.{h,cpp}`：只追一类行锁的获取、等待、释放，再读死锁/WFG。
5. `src/execution/execution_common.h` 及 DML executor 中的可见性、写冲突、undo 调用点。
6. `src/transaction/watermark.{h,cpp}`：最后理解低水位与版本回收，暂不触碰 sweeper 性能细节。

### 六次练习

| 次序 | 双会话场景 | 必须说清的内容 | 验收 |
|---|---|---|---|
| T1 | 单语句 DML | 隐式事务何时创建、何时提交或回滚 | 标出状态流转和 write set 生命周期 |
| T2 | `BEGIN` → 两条 DML → `COMMIT` | 显式事务的 `start_ts`、锁和日志何时处理 | 能解释为什么 BEGIN 必须是新快照 |
| T3 | `BEGIN` → DML → `ABORT/ROLLBACK` | undo 顺序、索引/记录恢复、锁释放 | 数据和索引均恢复到事务前 |
| T4 | 两事务更新同一行 | 写写冲突、年轻事务 abort 的原因 | 用现有一致性 C1/C2 类用例验证 |
| T5 | 一个读事务、一个写事务 | 可见性判断使用哪些时间戳，读者看见哪个版本 | 写出版本链的简图 |
| T6 | SER 下危险结构 | rw 反依赖在哪里登记，为什么必须语句级 abort | 说明不能拖到 COMMIT 再挑 victim |

### 方向验收

- 能口头区分 row lock、`TupleMeta`、undo log、watermark 各自的职责；
- 能解释 SI 下陈旧写必须 abort，及 SER 比 SI 多检查了什么；
- 能看懂一次 `TransactionAbortException` 后的清理链，不遗漏锁、undo 或状态；
- 可运行并说明 `python3 tests/local/consistency/run_consistency_regress.py --case C1 --case C2 --case H5` 覆盖的风险类型。

## 3. 方向三：WAL、刷盘与崩溃恢复

### 掌握目标

能用一句严谨的话回答：“为什么客户端收到 COMMIT 成功后，断电恢复仍应保留该事务？”并能定位一个日志类型从生成、刷盘到 redo/undo 的完整路径。

### 阅读顺序

1. [`6c.事务恢复调用链`](../Analysis/ProjectAnalysis/6c.事务恢复调用链.md) 的 WAL、恢复两节。
2. `src/recovery/log_defs.h`、`log_manager.h`：先整理日志类型、LSN、`LogRecord` 中最关键字段。
3. `src/recovery/log_manager.cpp`：按“追加 → 组提交/刷盘 → 等待稳定化”读取，特别画出 COMMIT ACK 的前置条件。
4. `src/storage/buffer_pool_manager.cpp`、`src/storage/disk_manager.cpp`：只看页面刷盘前的 WAL 检查和实际 I/O 边界。
5. `src/recovery/log_recovery.{h,cpp}`：按 analyze → redo → undo 的执行顺序读；挑 INSERT 或 UPDATE 一种日志完整追踪。
6. `tests/local/consistency/` 与恢复相关脚本：先读测试动作和断言，再回头阅读实现。

### 五次练习

| 次序 | 场景 | 必须说清的内容 | 验收 |
|---|---|---|---|
| R1 | 一条隐式 INSERT | 产生何种日志、页面何时变脏 | 画出 LSN 与页修改的先后 |
| R2 | 显式事务 COMMIT | commit log、稳定 LSN、ACK 的因果关系 | 写出 WAL 约束：日志先于对应脏页落盘 |
| R3 | 未提交事务中途崩溃 | 为何 redo 后还要 undo，如何识别 loser | 恢复后记录不存在 |
| R4 | 已提交事务中途崩溃 | redo 的幂等条件、为何不会重复应用 | 恢复后记录恰好存在一次 |
| R5 | UPDATE（尤其 delta/patch） | before/after 信息怎样支撑 redo 与 undo | 跟踪一个 UPDATE 日志类型的两个方向 |

### 方向验收

- 能解释 `LSN`、`persist_lsn`、dirty page、`fdatasync` 的关系，不把“写入内核缓冲”误当作持久化；
- 能画出一次崩溃恢复三阶段及各阶段输入/输出；
- 能从恢复测试失败现象反查：是日志没稳定、redo 不全、undo 错误，还是测试环境没有真正重启；
- 只在隔离测试目录中做 kill/restart 演练，绝不对当前重要数据库目录进行破坏性测试。

## 6. 现场题的 90 分钟执行模板

1. **0–10 分钟：读题与定边界。** 写下输入、输出、异常、是否影响事务/存储；用代码地图找最接近的已实现功能。
2. **10–25 分钟：画最小影响链。** 从 parser 或入口到测试逐层列文件；先读相邻功能，禁止凭印象跨层改代码。
3. **25–55 分钟：最小实现。** 一次只改 1–2 个相关文件；保留现有接口和错误风格；不做清理性重构。
4. **55–75 分钟：定向验证。** 覆盖正常、边界、非法输入，以及题意相关的事务/重复执行情形。
5. **75–90 分钟：回归与提交检查。** Release 编译、基础回归、删除日志和硬编码；逐项对照题意确认输出与错误行为。

出现问题时，按以下顺序排查：**输入是否真的到达分支 → 中间对象是否正确构建 → executor/存储状态是否变化 → 错误是否被吞掉 → 测试是否连到正确的新进程和数据库目录**。
