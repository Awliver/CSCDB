## 归因裁决

### 1. T0：❌ 永久放弃

- `35,000.8 → 24,508.8`，相对直接父代码回退 **29.98%**。
- 三轮分别回退 **25.68% / 22.91% / 29.98%**，不是单轮噪声。
- attempted 下降 25.31%，committed 下降 26.33%，但异常放弃率只增加 0.93 个百分点；主因是服务能力下降，不是业务回滚或冲突率突变。
- CPU 平均下降 31.85%，p50 上升 22.25%，p99 上升 47.12%。T0 的 60s I/O 诊断中，9,649 次 `fdatasync` 合计占 55.756s，呈现明显阻塞。
- 该提交不是纯观测改动：同时改动事务/WAL/CTS/recent-writes 路径，并将行锁回收节奏从每 5 秒一次改为每 1 秒一次。其诊断价值不足以抵偿排名路径扰动。

**处理**：不修补、不复测、不合并；活动主线保持在不含 T0 的 `0bfab08`。本地与远端 `oj_split_T0`、`ultra_test_full_stack_safety` 分支及本地 `local/full-stack-safety` 标签均已删除；R1/S1/S2/L1/P-W1 独立分支不受影响。

### 2. `4bf77ac`：LOAD 收益成立，排名稳定性未通过

- LOAD 从 620.61s 降到 107.25s，改善 **82.72%**，装载功能与恢复门禁通过。
- 排名中位相对 `c446377` 下降 **13.07%**，不能替换性能锚点。
- R1 为 43,502、5s CV 仅 3.72%，但 R2/R3 降为 31,629.6 / 35,000.8，CV 升至 36.88% / 33.92%。这说明峰值能力仍在，长窗口存在明显抖动。
- 后续若继续拆分 LOAD 修复，应保留 CSV/bulk-index/RmScan 优化，单独验证 buffer cleaner 批量写；不得把整版 `4bf77ac` 直接升级为排名基线。

## 后续纪律

1. 所有新实验以 `c446377` 的 40,264.8 为性能回退锚点，并以不含 T0 的干净父版本分支。
2. 观测代码默认关闭时不得改变锁回收周期、WAL 决策、事务语义或后台清扫算法。
3. 本地短窗只能筛除明显错误；正式结论以 W=50×32、3×150s OJ 单变量对照为准。
4. 任一轮退化超过 2%、p99 恶化超过 10% 或中位无至少 5% 收益，均不得上线。
