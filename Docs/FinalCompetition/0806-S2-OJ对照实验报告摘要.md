## 性能裁决

- 中位 `35,000.8 → 24,668.8`，相对直接父对照回退 **29.52%**；三轮按轮比较分别为 **-26.59% / -22.01% / -31.46%**，全部远超“任一轮不得退化 >2%”门槛。
- 总 attempted 下降 **26.07%**，committed 下降 **26.83%**，异常放弃率却只增加 **0.71 个百分点**。退化来自固定窗口内整体服务能力降低，不是 abort 口径突变。
- CPU 平均下降 **29.15%**，平均延迟上升 **41.98%**，p99 上升 **83.89%**；R1→R3 的 5s CV 又从 41.36% 增至 66.29%，呈现等待、阻塞和运行期稳定性共同恶化。
- LOAD 和峰值 RSS 虽分别改善 18.94% 与 14.14%，但资源下降没有转化为 Rank，不能抵扣排名路径的显著回退。
- 可选 I/O 窗口记录 9,395 次 `fdatasync`、累计 55.492s；父对照的该阶段采集失败，不能凭单份系统调用报告把回退精确归因到 WAL。

## 单变量边界

该提交并不是可归因的最小 S2 补丁：相对父版本改动 4 个文件，新增/改写约 850 行，除 `recent_writes` 分片与增量清扫外，还携带 T0 的 runtime telemetry、事务 begin/commit/abort、CTS 和显式事务计数重构。其中 `runtime_stats.h` 与 `transaction.h` 和 T0 字节一致，事务管理器主体也高度重合。

S2 的中位 **24,668.8** 与已证伪 T0 的 **24,508.8** 仅相差 **0.65%**。因此，本次结果足以永久否决 `83a3c99` 整个候选分支，但不能严谨宣称约 30% 回退全部由 `recent_writes` 分片算法单独造成。后续不得从该提交继续修补；若未来重新提出同类机制，必须从干净父版本重新制作只包含目标数据结构的最小补丁，并重新完成同规格 A/B。

## 处理结果

1. `oj_split_S2` 从未合并到活动主线；`c446377` 的 **40,264.8 NewOrder/min** 继续作为性能回退锚点。
2. 不修补、不复测、不合并 `83a3c99`；本地与 GitLab 远端 `oj_split_S2` 分支均已删除，代码不再保留于活动引用。
3. 后续独立候选不得叠加 S2 或其携带的 T0 事务/统计骨架，必须从不含实验代码的 `0bfab08` 或对应干净父代码出发。
4. 当前基线中的既有 MVCC sweeper 与 `recent_writes_` 正确性/内存稳定性设施保持冻结有效；本次清退的是替代实现 `oj_split_S2`，不删除主线已有机制。
