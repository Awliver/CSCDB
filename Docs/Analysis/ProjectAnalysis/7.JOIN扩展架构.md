# JOIN 扩展架构

> **状态（2026-08-12）**：在原 INNER/LEFT/RIGHT/CROSS/FULL 架构上继续加入 NATURAL、LEFT/RIGHT SEMI、LEFT/RIGHT ANTI 与相关 LATERAL 派生表。扩展功能由 `tests/run_tests.py` 的两组 JOIN 回归覆盖，本地完整功能测试为 **13/13 PASS**。

本文描述当前代码，而不是待实现方案。JOIN 已经贯通 Parser、Analyze、Planner、Portal 和 Executor，并建立了供外连接使用的逐列 NULL 协议。

---

## 一、支持范围

当前 FROM 语法支持：

```sql
table1, table2
table1 JOIN table2
table1 CROSS JOIN table2
table1 JOIN table2 ON ...
table1 INNER JOIN table2 ON ...
table1 LEFT [OUTER] JOIN table2 ON ...
table1 RIGHT [OUTER] JOIN table2 ON ...
table1 FULL [OUTER] JOIN table2 ON ...
table1 NATURAL [INNER|LEFT|RIGHT|FULL [OUTER]] JOIN table2
table1 [LEFT|RIGHT] SEMI JOIN table2 ON ...
table1 [LEFT|RIGHT] ANTI JOIN table2 ON ...
table1 [INNER|LEFT|CROSS] JOIN LATERAL (SELECT ... FROM ... WHERE ...) alias [ON ...]
(joined_table) JOIN table3 ON ...
```

关系可以使用 `AS alias` 或省略 `AS`。ON/WHERE 条件当前是比较表达式的 AND 链，比较符支持 `=、<>、<、>、<=、>=`；JOIN 的 ON 还接受常用的 `ON TRUE`。

`SEMI JOIN` / `ANTI JOIN` 不写 LEFT/RIGHT 时默认保留左侧。LATERAL 当前支持相关列出现在派生查询 WHERE 的比较 AND 链中，并完整支持派生查询内部的聚合、ORDER BY 与 LIMIT；RIGHT/FULL、NATURAL/SEMI/ANTI LATERAL 以及相关列出现在 SELECT/GROUP/HAVING/ORDER BY/内部 ON 的形式会明确报错。相关名解析以当前 LATERAL 直接左子树为边界，不穿透多层 LATERAL 引用祖先作用域。

当前仍没有实现 `USING`、普通（非 LATERAL）FROM 派生表、表函数、`OR/NOT` 和 `IS NULL`。外连接的物理算法目前只有 NLJ；INLJ 只用于普通 INNER JOIN，且右侧索引遵循赛题的唯一索引约束。

## 二、跨层数据流

```text
SQL
 │
 ▼
Parser
 FromExpr
 ├─ TableRef(physical table, alias)
 ├─ LateralRef(select, alias)
 └─ JoinExpr(type, natural/lateral, left, right, on_conds)
 │
 ▼
Analyze
 AnalyzedFrom + AnalyzeScope
 ├─ TableBinding(table_name, binding_name)
 ├─ 递归作用域/歧义/类型检查
 └─ ON 条件与 WHERE 条件分离
 │
 ▼
Planner
 ├─ ScanPlan(物理表名 + 关系实例名)
 ├─ JoinPlan(逻辑 JoinType + 物理 PlanTag)
 ├─ FilterPlan(不能安全下推的 WHERE)
 ├─ ProjectionPlan
 └─ NLJ / INLJ 选择、INNER/CROSS 重排、外连接屏障
 │
 ▼
Portal
 Plan Tree 递归转换为 Executor Tree
 │
 ▼
Executor
 ├─ NestedLoopJoinExecutor：INNER/CROSS/LEFT/RIGHT/FULL/SEMI/ANTI/NATURAL
 ├─ LateralNestedLoopJoinExecutor：逐左行重启右侧完整子计划

 │
 ▼
QlManager / Wire
 NULL 单元格编码为 present=0，文本输出为 NULL
```

## 三、Parser：保留 JOIN 的结构与边界

### 3.1 AST

`src/parser/ast.h` 中的 FROM 节点分为：

- `TableRef`：真实表名和可选别名。
- `LateralRef`：带必需别名的 SELECT 派生表。
- `JoinExpr`：`JoinType`、左右子树、属于当前节点的 `on_conds`，以及正交的 `natural/lateral` 标志。
- `SelectStmt::from`：完整 FROM 根节点。

`JoinType` 是逻辑语义：`INNER_JOIN / LEFT_JOIN / RIGHT_JOIN / FULL_JOIN / CROSS_JOIN / LEFT_SEMI_JOIN / RIGHT_SEMI_JOIN / LEFT_ANTI_JOIN / RIGHT_ANTI_JOIN`。NATURAL 与 LATERAL 是修饰属性，不伪装成新的互斥 JoinType。

### 3.2 结合顺序

未加括号的连接按 grammar 左结合构造；括号可以显式形成子树。每个 `JoinExpr` 只拥有紧跟该 JOIN 的 ON 条件，为 Analyze 和 Planner 保留外连接边界。

## 四、Analyze：关系实例、作用域和条件语义

### 4.1 关系实例

同一物理表可以在一条 SQL 中出现多次：

```sql
FROM employee e1
JOIN employee e2 ON e1.manager_id = e2.id
```

因此 Analyze 使用：

```cpp
TableBinding {
    table_name;    // 物理表 employee
    binding_name;  // SQL 关系实例 e1/e2
}
```

扫描和列解析使用 `binding_name`，存储访问、索引和 MVCC 使用 `table_name`。这条边界是自连接正确性的基础。

### 4.2 递归作用域

`analyze_from()` 后序遍历 AST：

1. 表叶节点读取元数据并把列限定符改为 binding。
2. JOIN 节点分别分析左右子树，再由 `merge_scopes()` 合并。
3. 重复 binding 立即报错。
4. ON 中的列只能引用当前 JOIN 左右子树已经可见的关系。
5. 未限定列在多个关系中同名时报 `AmbiguousColumnError`。
6. 比较两端执行列存在性和类型检查。

输出的 `AnalyzedFrom` 与 AST 同构，但已经完成名称绑定，Planner 不需要重新猜测列属于哪张表。

### 4.3 ON 与 WHERE 分离

`Query` 同时保存：

- `from`：带每层 ON 条件的语义 Join Tree。
- `where_conds`：整棵连接完成后才生效的 WHERE。
- `conds`：兼容旧路径的扁平视图，不作为外连接规划的语义来源。

例如：

```sql
-- 保留未匹配的 a 行
a LEFT JOIN b ON a.id=b.id AND b.score>60

-- NULL 扩展后再过滤，未匹配的 a 行被删除
a LEFT JOIN b ON a.id=b.id WHERE b.score>60
```

二者不能合并，否则 LEFT JOIN 会被错误地改写成近似 INNER JOIN。

## 五、Planner：从语义树到物理 Plan Tree

### 5.1 Plan 节点职责

| 节点 | 关键字段 | 职责 |
|------|----------|------|
| `ScanPlan` | `tab_name_`、`binding_name_` | 分离物理表与 SQL 关系实例 |
| `JoinPlan` | `type`、`tag`、`left_`、`right_`、`conds_` | `type` 表示逻辑 JOIN；`tag` 表示 NLJ/INLJ |
| `FilterPlan` | `subplan_`、`conds_` | 保存不能越过外连接的 WHERE |
| `ProjectionPlan` | `sel_cols_` | JOIN 前后裁列，并保持最终列顺序 |

逻辑类型与物理算法必须分离。`LEFT_JOIN` 不能用一个 PlanTag 同时表示“左外连接”和“采用 NLJ”。

### 5.2 谓词下推规则

单关系 ON 谓词的安全下推矩阵：

| JOIN 类型 | 左侧 ON 谓词 | 右侧 ON 谓词 |
|-----------|:------------:|:------------:|
| INNER | 可下推 | 可下推 |
| LEFT | 不可下推 | 可下推 |
| RIGHT | 可下推 | 不可下推 |
| FULL | 不可下推 | 不可下推 |

WHERE 只有在从 Join Tree 根到目标关系的路径上从未经过该关系作为 NULL-supplying side 时才能进入 Scan。其余条件保留在 JOIN 上方的 `FilterPlan`。

### 5.3 连接顺序

- 纯 INNER/CROSS 子树可以展开并贪心重排。
- 优先选择估算行数小、与当前子树有连接条件、右侧存在可用索引的关系。
- 跨表 WHERE 可以把 CROSS JOIN 转换为 INNER JOIN 条件。
- LEFT/RIGHT/FULL、SEMI/ANTI、NATURAL 与 LATERAL 都是重排屏障，不能跨越边界交换关系。
- 外连接左右内部的纯 INNER/CROSS 子树仍可独立优化。

当前基数估算使用页数、每页记录数和固定选择率，是轻量启发式，不是统计直方图优化器。

### 5.4 NLJ 与 INLJ

`make_join_plan()` 只在以下条件同时成立时选择 INLJ：

1. 逻辑类型是 INNER JOIN。
2. 右侧最终可识别为叶子 `ScanPlan`。
3. ON 中存在连接到右侧索引列的等值条件。
4. 扫描常量条件与连接键满足索引最左前缀。
5. 当前事务/MVCC/SSI 模式允许使用该索引路径。

LEFT/RIGHT/FULL、SEMI/ANTI、NATURAL 与 LATERAL 当前统一选择 NLJ；只有普通 INNER JOIN 进入 INLJ 候选路径。

## 六、Executor：外连接状态机

`NestedLoopJoinExecutor` 在 `beginTuple()` 中物化右子树，同时保存每行的 NULL 掩码。执行过程分为四步：

1. 读取一行左输入，扫描右侧缓冲区。
2. ON 成立时输出拼接行，并标记当前左行和对应右行为 matched。
3. 扫描结束仍未匹配时，LEFT/FULL 输出一行“右侧全 NULL”。
4. 所有左行结束后，RIGHT/FULL 遍历 `right_matched_`，为每个未匹配右行输出“左侧全 NULL”。

输出状态由 `OutputKind` 表示：

- `MATCHED`
- `LEFT_NULL_EXTENDED`
- `RIGHT_NULL_EXTENDED`

记录缓冲区中 NULL 一侧的字节会清零，但零值不是 NULL 的语义来源；真正语义由 `current_nulls_` 保存。因此整数 `0` 可以正常与 `0` 匹配，而 NULL 永远不会与 `0` 匹配。

ON 遵循当前条件系统可表达范围内的 SQL 三值逻辑：任一操作数为 NULL，结果视为 UNKNOWN；对 JOIN 是否匹配而言 UNKNOWN 与 false 相同。

右侧物化使 RIGHT/FULL 的未匹配行追踪简单可靠，代价是空间复杂度 `O(|R|)`；当前实现适合功能题和中小关系，不等同于面向大表的 Hash Join。

## 七、逐列 NULL 协议

`AbstractExecutor::null_mask()` 返回当前输出行、按 `cols()` 顺序排列的布尔掩码。`nullptr` 表示当前行没有 NULL。

| 算子 | NULL 职责 |
|------|-----------|
| `NestedLoopJoinExecutor` | 生成并合并左右掩码 |
| `IndexNestedLoopJoinExecutor` | 消费左子树掩码；NULL 连接键不点查索引 |
| `FilterExecutor` | NULL 比较结果为 UNKNOWN/false；转发保留行掩码 |
| `ProjectionExecutor` | 按投影列索引重排掩码 |
| `SortExecutor` | 记录与掩码一起缓存、交换和输出；ASC NULLS LAST、DESC NULLS FIRST |
| `AggExecutor` | COUNT(column)、SUM/MIN/MAX/AVG 忽略 NULL；GROUP BY NULL 形成独立组 |
| `LimitExecutor` | 原样转发掩码 |
| `UnionExecutor` | NULL 位参与去重键；输出时恢复掩码 |
| `QlManager/Wire` | 文本输出 `NULL`；Wire 单元格 `present=0` |

任何新增会缓存、重排或拼接记录的算子，都必须同步处理 NULL 掩码，否则外连接在下一层会退化成零值连接。

## 八、验证边界

统一功能测试 `tests/run_tests.py` 覆盖：

- CROSS/INNER/LEFT/RIGHT/FULL 及可选 OUTER。
- NATURAL 的公共列合并、RIGHT/FULL COALESCE、无公共列与嵌套连接。
- LEFT/RIGHT SEMI/ANTI 的重复键、空侧、隐藏非保留侧与下游连接。
- LATERAL 的逐左行 Filter/Aggregation/Sort/Limit、LEFT 补行及非法方向。
- 六种比较符、别名、自连接、重复键、三表和括号连接。
- ON/WHERE 差异、空输入、NULL 扩展。
- 聚合、GROUP BY、排序、LIMIT 和唯一索引 INLJ。
- 歧义列、重复 binding、未知 binding 和非法 JOIN。

验证结论分两层：

- **OJ 证据**：基本 JOIN 已通过，说明扩展没有破坏原赛题主路径。
- **本地证据**：基础与扩展 JOIN 随完整功能测试 13/13 PASS；OJ 没有对这些新增语义做专项背书。

仍需记住两个系统边界：

1. 赛题索引是唯一索引；不能用重复键索引验证 INLJ。无索引 NLJ 可以正常产生多对多结果。
2. INNER/CROSS 重排会改变物理计划形状。若某一评测严格要求按 SQL 书写顺序输出 EXPLAIN，应以该题规范决定是否关闭重排，而不是改变 JOIN 结果语义。
